## 1. (Bug) ตัวละครเดินชนกันจะโดนอีกตัวละครลากไปด้วย

**ต้นฉบับ:** "ตัวละครเดินชนกันจะโดนอีกตัวละครลากไปด้วย"
**แปล (EN):** When two avatars collide while walking, one gets dragged along by the other instead of just passing through / stopping.

**Root cause (confirmed):** `zyra-app/zyra-engine/pixi-game/scene.ts:3536-3615` — `_tickOverlapTimer` / `_pushIfOccupied`.
- ผู้เล่นเดินทับกันได้ตลอดเวลาที่ "กำลังเดิน" (by design) แต่ทันทีที่ผู้เล่นคนใดคน "หยุดนิ่ง" บน tile ที่อีกฝ่าย claim ไว้ (`occupiedByRemote`) เกิน 0.15s ระบบจะ auto-issue การเดิน 1 ก้าวให้ฝ่ายที่ "มาถึงทีหลัง" (เทียบ `arrivedAt`)
- `startRemotePathMovement` (`scene.ts:4429-4440`) stamp `arrivedAt` ตอน**เริ่มเดิน** (ไม่ใช่ตอนถึงจริง) และ claim tile ปลายทางทันที
- ตัวการหลัก: `_pushIfOccupied` (`scene.ts:3595-3601`) เลือกทิศ dodge โดยเริ่มจาก `faceOffset[this.pDir]` — **ทิศที่กำลังเดินอยู่เดิม** ก่อนทิศอื่น ทำให้ฝ่ายที่ต้อง dodge ถูกเดินต่อไปอีก 1 ช่อง "ในทิศทางเดียวกับที่กำลังเดินเข้ามา" ไม่ใช่หนีออกจากอีกฝ่าย — เกิดซ้ำๆ ในจุดคับแคบ (ประตู/ทางเดิน) จนดูเหมือน "ถูกลากไปด้วย"

**Fix:** เปลี่ยนลำดับทิศ dodge เป็นทิศตรงข้ามกับตำแหน่งอีกฝ่าย (คำนวณจากตำแหน่งจริง ไม่ใช่ facing direction เดิม)

## 2. (Bug) เห็นเพื่อนลอยได้

**ต้นฉบับ:** "เห็น เพื่อนลอยได้"
**แปล (EN):** Sometimes a friend's avatar appears floating (stuck at a stale position, not aligned to the ground/tile).

**Root cause (confirmed):** `zyra-app/zyra-engine/pixi-game/scene.ts:4216-4223` — resync branch ใน `setRemotePlayers` เขียนแค่ `existing.sprite.x/y` ตรงๆ แต่ **ไม่ได้เขียน** `existing.px`/`existing.py` — ขณะที่ `_renderUpdate` (`scene.ts:2423-2424`) รันทุกเฟรมและทับ `rp.sprite.x = rp.px; rp.sprite.y = rp.py` แบบไม่มีเงื่อนไข ค่าที่ resync เขียนไปถูกทับด้วยค่าเก่า (stale) ทันที — เพื่อนที่หายจากจอ (สลับแท็บ/AOI cell เปลี่ยน) แล้วโผล่มาใหม่จะค้างตำแหน่งเดิมก่อนหาย

**Fix:** เพิ่ม `existing.px = px; existing.py = py` คู่กับการเขียน `sprite.x/y` ในบล็อก resync

**Secondary (confidence ~30%):** remote player ที่นั่งไม่มี sort-row override เหมือน local player (`pSitObjectSortRow`) — อาจทำให้เพื่อนนั่งเก้าอี้ sort ผิด layer ดูเหมือนลอยเหนือเก้าอี้ — ต้อง verify เพิ่มถ้ายังเจออาการหลัง fix หลัก

## 3. (Bug) เปลี่ยนชื่อแล้วชื่อไม่เปลี่ยน — จอตัวเองเปลี่ยน แต่เพื่อนเห็นไม่เปลี่ยน

**ต้นฉบับ:** "เปลี่ยนชื่อแล้วชื่อไม่เปลี่ยน แต่ที่จอตัวเองเปลี่ยน แต่เพื่อนเห็นไม่เปลี่ยน"
**แปล (EN):** After changing display name, own screen updates correctly but other already-connected users still see the old name.

**Root cause (confirmed):** ไม่มี broadcast mechanism สำหรับชื่อที่เปลี่ยนกลางเซสชันเลย (missing feature, ไม่ใช่ broken broadcast)
- `zyra-ws/internal/hub/hub.go:133-147` (`Join`) set `Client.DisplayName`/`Client.CharacterName` ครั้งเดียวตอน connect แล้วไม่มีจุดใดใน `zyra-ws/internal` เขียนทับอีกเลย
- ชื่อที่ peer อื่นเห็น (nameplate, chat sender name ผ่าน `EffectiveName()`) อ่านจาก field ที่ freeze ไว้นี้ตลอด session
- 2 endpoint แก้ชื่อฝั่ง zyra-api (`profile_handler.go` global `display_name`, `workspace_member_handler.go` workspace-scoped `character_name`) เป็นแค่ DB update ธรรมดา ไม่มี HTTP/Redis call แจ้ง zyra-ws
- ฝั่ง client (`vo-profile-tab.tsx`) หลัง save สำเร็จเรียกแค่ `useUserStore.patchUser()` (local state) — ไม่เคยแจ้ง WS

**Fix:** เพิ่ม WS message ใหม่ `profile_updated` (mirror pattern ของ `status`/`status_changed` ที่มีอยู่แล้ว) broadcast ไปทุก peer ที่ connect อยู่ — ดูข้อ 6 ด้านล่าง (รวม fix เดียวกัน)

## 4. (Bug) เวลาอยู่ห้องประชุม ห้องชอบล็อกเอง

**ต้นฉบับ:** "เวลาอยู่ห้องประชุม ห้องชอบล็อกเอง"
**แปล (EN):** While inside a meeting room, the room keeps locking itself automatically, with no one manually locking it.

**Root cause (confirmed):**
- `tb_zone_section.is_locked` มี `DEFAULT TRUE` (migration 63) — ห้องใหม่ล็อกเสมอตาม design
- `EnterZone`'s upsert ไม่ set `is_locked` เวลา insert แถวใหม่ → ใช้ column default (TRUE) ทุกครั้งที่แถวถูกสร้างใหม่
- **จุดที่ทำให้ "ล็อกเอง":** `SetPresence` (`zone_section_service.go:501-512`) ลบแถว `tb_zone_section` ทิ้งทันทีเมื่อ online member เหลือ 0 คน (ทุกคน away/offline ชั่วคราว — แท็บถูก throttle ตอน background, เน็ตสะดุด, หรือ `onReconnected` เรียก cleanup เป็น side-effect) แล้วเมื่อมีคนเดินเข้าห้องอีกครั้ง `EnterZone` จะสร้างแถวใหม่ที่ล็อกอยู่เสมอ (default TRUE) — สถานะ unlock ที่เจ้าของห้องปลดล็อกไว้ก่อนหน้าหายไปเลย

**Fix:** เอา `DELETE FROM tb_zone_section` ใน `SetPresence` (เมื่อ online=0) ออก ปล่อยให้แถว (พร้อม `is_locked` เดิม) อยู่ต่อ แล้วให้ `CleanupStaleSections`/`CleanupStaleGlobally` (TTL-based, มี grace period ถูกต้องอยู่แล้ว) เป็นจุดเดียวที่ลบ session จริงๆ

## 5. (Bug) เวลาอยู่ห้องประชุม สเตตัสชอบเปลี่ยนเป็นไม่ว่าง ทั้งที่จริงว่าง

**ต้นฉบับ:** "เวลาอยู่ห้องประชุม สเตตัสชอบเปลีย่นเป็นไม่ว่าง แต่จริงๆว่าง"
**แปล (EN):** While inside a meeting room, the user's status keeps flipping to "busy" even though they're actually available.

**Root cause (confirmed — race condition):**
- Force-clear ตอนเข้าห้องประชุมทำงานถูกต้อง (`hero-virtual-office.tsx:6687-6693`) — เดิน "เข้า" meeting zone ครั้งแรก (zone transition) จะ clear busy/away → available เสมอ
- แต่ effect "restore saved status จาก DB" (`hero-virtual-office.tsx:3161-3188`) รันแยกอิสระตอน mount — ถ้า `getProfile()` (async) resolve ช้ากว่าตอนที่ผู้เล่น spawn เข้ามาแล้วอยู่ **ในห้องประชุมอยู่แล้วตั้งแต่แรก** (เช่น last_position บันทึกไว้ในห้องประชุม) การ clear busy/away ที่ผูกกับ zone transition จะไม่ re-fire อีก (ไม่มี transition เกิดขึ้น) — ค่า `busy` เก่าจาก DB จึงถูก apply ทับโดยไม่มีอะไรมาเคลียร์อีก

**Fix:** ใน effect restore-status ทั้ง 2 branch เพิ่มเช็ค: ถ้า `savedStatus` เป็น busy/away และ `activeZoneRef.current?.zone_type === "meeting"` ให้บังคับเป็น available ก่อน apply/broadcast

**Secondary:** `onReconnected` ไม่เคย resend `setStatus()` หลัง reconnect — เพื่อนอาจเห็นสถานะ default ชั่วคราว (แก้เพิ่มพร้อมกัน)

## 6. (Bug) เปลี่ยนรูปโปรไฟล์แล้วคนอื่นไม่เห็นทันที

**ต้นฉบับ:** "เปลี่ยนรูปโปรไฟล์แล้วคนอื่นไม่เห็นทันทีไปด้วย" (เพิ่มเข้ามาระหว่าง plan review)
**แปล (EN):** After changing profile picture, other already-connected users don't see the new picture immediately.

**สำคัญ:** อย่าสับสนกับ `AvatarURL`/`avatar_url` ใน zyra-ws — นั่นคือ walking/sitting spritesheet ของตัวละคร ซึ่ง broadcast real-time อยู่แล้วผ่าน `move`/`moved` protocol (มี test ยืนยัน `TestHandleMove_AvatarURLChangeBroadcastsJSONImmediately`) — ส่วนนั้นไม่มีบั๊ก

**Root cause (confirmed):** รูปโปรไฟล์ (headshot) ที่เห็นใน member panel/chat/facepile มาจาก field `avatar_url` ของ `listWorkspaceMembers()` ซึ่งฝั่ง DB คือ `COALESCE(u.image_upload, '') AS avatar_url` (`workspace_member_service.go:142`) — คนละ field กับ WS avatar_url ข้างบนโดยสิ้นเชิง
- `hero-virtual-office.tsx:3103-3126` fetch `listWorkspaceMembers()` เข้า `allWorkspaceMembers` **ครั้งเดียวตอน mount session** ไม่มี refetch/invalidate อีกหลังจากนั้น — เหมือนข้อ 3 (ชื่อ) เป๊ะ แค่คนละ data source

**Fix (รวมกับข้อ 3 — ใช้ WS broadcast เดียวกัน):**
1. `zyra-ws/internal/hub/message.go` — เพิ่ม `ClientMsgProfileUpdated = "profile_updated"` (inbound) / `MsgProfileUpdated = "profile_updated"` (outbound) payload: `display_name`, `character_name`, `avatar_url` (photo — ไม่ใช่ spritesheet)
2. `zyra-ws/internal/hub/room.go` — handler ใหม่ `handleProfileUpdated` mirror `handleStatus`: update `c.DisplayName`/`c.CharacterName` แล้ว broadcast ไปทุก peer (ไม่แตะ `c.AvatarURL` ของ spritesheet)
3. `zyra-app/lib/api/workspace-ws.ts` — method `notifyProfileUpdated(displayName, characterName, avatarUrl)`
4. `zyra-app/views/user/virtual-office/hero-virtual-office.tsx` — รับ broadcast แล้ว patch `scene.ts` roster displayName + `allWorkspaceMembers` state (patch ที่เดียว ไหลไปทุก UI ที่ derive จาก state นี้)
5. หลัง `updateProfile()`/`updateMyCharacterName()` สำเร็จ เรียก `notifyProfileUpdated(...)` ทันที
