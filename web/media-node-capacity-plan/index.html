ลำดับที่ตัดสินใจไว้แล้ว: ลองของฟรีก่อน วัดผล แล้วค่อยจ่ายเงิน

ทีมสรุปไว้เองว่า SFU โต CPU 2 เท่าใน 3 วันอาจมาจาก video fan-out ที่ “ถาวรหรือชั่วคราวก็ยังไม่รู้” ทางแก้ที่ทำก่อนคือลด camera capture จาก 1080p → 720p (ฟรี, ไม่มี downtime, revert ง่าย) แล้วค่อยดูว่า CPU ของ SFU คืนมาพอไหม — ถ้าไม่พอหรือโหลดยังโตต่อ ค่อยเข้าสู่ตัวเลือกที่ต้องจ่ายเงิน (PR #29-31 หรือขยาย node เดิม)

เกตวันนี้ 720p live บน dev/uat เท่านั้น (ขึ้น uat 09-20) ยังไม่ขึ้น prod — แปลว่ายังไม่เคยวัดผลจริงบนโหลดจริงเลยสักครั้ง เกตนี้ยังไม่ผ่าน
ข้อเสนอ: ให้เกตนี้เป็นเงื่อนไขก่อนสาน PR #29-31 หรือขยาย node

ขึ้น 720p บน prod (merge develop → main แล้ว tag v*) → รอ 3-5 วันทำการที่มี peak hour จริง → วัด SFU cores ที่ 17:00 เทียบ baseline เดิม (1.095 core, 09-18) ถ้ายังเกิน ~0.8-0.9 core ที่ participants ใกล้เคียงเดิม (40-50 คน) แปลว่า workload โตจริงไม่ใช่แค่ 1080p ลาก — ให้เข้าสู่แผน Option B ด้านล่างทันที

Runbook ละเอียด

Option B — สาน PR #29 → #30 → #31 แนะนำ

Blocker ที่ต้องแก้ก่อนอันดับแรก

terraform.tfstate อยู่ที่ไหน — ต้องรู้ก่อน apply แม้แต่ครั้งเดียว

PR #29 เตือนไว้ตรง ๆ ว่า terraform.tfstate เป็น local + gitignored และไม่อยู่ใน checkout นี้ — ถ้า apply จากเครื่องที่ไม่มี state ไฟล์เดิม Terraform จะเข้าใจว่ายังไม่มีอะไรอยู่เลย แล้วพยายามสร้าง zyra-k3s, IP, firewall, AlloyDB ใหม่ทั้งหมด — ทับของจริงที่รันอยู่

ต้องทำก่อนหา state ไฟล์ตัวจริงว่าใครรัน apply ล่าสุดจากเครื่องไหน แล้ว migrate ไป GCS backend (มี block backend "gcs" comment ไว้รอแล้วใน terraform/versions.tf:17) ในการ apply เดียวกับที่เพิ่ม media node — ห้ามข้ามขั้นตอนนี้ไม่ว่ากรณีใด
  1. ยืนยันตำแหน่ง state จริง + migrate เข้า GCS backend ตามที่เตรียม comment ไว้ใน versions.tf คาดหวัง: terraform plan จากเครื่องไหนก็ได้ผลตรงกัน ไม่มี resource ที่จะถูก "สร้างใหม่" ทั้งที่มีอยู่แล้ว
  2. merge PR #29 แล้ว apply — สร้าง VM ตัวที่ 2 เท่านั้น ยังไม่มี workload ย้าย คาดหวัง: kubectl get nodes เห็น node ใหม่ label zyra.center/role=media พร้อม taint สถานะ Ready · node1 ยังทำงานปกติทุกอย่างเหมือนเดิม
  3. เติม join token เข้า Secret Manager ตามคำสั่งที่ระบุไว้ใน k3s-agent-vm.tf (SSH เข้า server node ดึง /var/lib/rancher/k3s/server/node-token) คาดหวัง: agent node join สำเร็จโดยไม่ต้อง reboot ซ้ำ
  4. merge PR #30 (chart passthrough) — ตาม PR เอง verify แล้วว่า byte-identical กับปัจจุบัน คาดหวัง: Argo ไม่ sync อะไรเลยสักตัว (no diff) — ถ้ามี diff แปลว่ามีอะไรผิดจากที่ PR อ้าง ต้องหยุดตรวจก่อน
  5. นอกเวลางาน (หลัง 22:00 ไทย หรือช่วงเดียวกับ SFU nightly restart 04:00) un-draft แล้ว merge PR #31 — จุดเดียวที่มี downtime จริง คาดหวัง: ~30 วินาที ห้องประชุมสดทุกห้องหลุด แล้วกลับมาเชื่อมต่อใหม่บน media node
  6. Verify ครบตามที่ PR #31 กำหนดไว้เอง: kubectl get pod -n sfu -o wide อยู่บน media node · ประชุมจริง 2 เครื่องคนละเน็ต ทดสอบเสียง/วิดีโอ/แชร์จอ · chrome://webrtc-internals selected candidate ต้องเป็น IP ของ media node · บังคับ TURN relay (บล็อก UDP) แล้วเช็ค backend service HEALTHY ถ้า webrtc-internals ยังโชว์ IP node เดิม = rtc.use_external_ip ผิด ต้องแก้ livekit-prod.yaml ก่อนไปต่อ
  7. รอ 24 ชม. แล้วเติมตาราง before/after ลงในเอกสารนี้ (prod restart ต้องยังเป็น 0) คาดหวัง: node1 cpu requests ลดลงเยอะ (ไม่มี SFU 1000-2000m ค้างอยู่แล้ว) — เก็บตัวเลขไว้เทียบ
  8. เปิด PR-4 (ยังไม่มี): คืน cpu request/limit ของ prod app/api/ws บน node1 กลับไปใกล้เคียงค่าก่อนเหตุการณ์ 09-10 เพราะไม่ต้องแย่งกับ SFU อีกแล้ว ผล: node1 มี headroom เยอะขึ้นมาก เผื่อ scale prod เพิ่ม replica ได้ในอนาคต
  9. เปิด PR-5 (ยังไม่มี): alert แยกต่อ node (media node ล้ม / node1 ล้ม แยกกัน) ตามที่ PR #29 วางลำดับไว้ ผล: รู้ทันทีว่า node ไหนมีปัญหา ไม่ต้อง SSH เข้าไปดูเอง
Rollback (จาก PR #31 เอง)

Revert PR #31 → Argo ย้าย SFU pod กลับไป node1 อัตโนมัติ (ไม่มี taint กันไว้) แลกกับ downtime อีก ~30 วิ · TURN ไม่หลุดเพราะ instance group ใน PR #29 ถือทั้ง 2 node ไว้อยู่แล้วไม่ว่า SFU จะอยู่ node ไหน
