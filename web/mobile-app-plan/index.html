Zyra Mobile Plan

เลือกแนวทางทำ Zyra World เป็นแอปมือถือที่ขึ้น App Store และ Play Store พร้อม Virtual Office เต็มรูปแบบ เปรียบเทียบ Expo, Flutter, Capacitor และตัวเลือกอื่น โดยอิงจากโค้ดจริงใน zyra-app

วันที่ 2026-09-29 scope: Full Virtual Office target: iOS + Android store ทีม: ทำได้ทุก stack
มติ 2026-09-29 — เลือก Capacitor + native feature จริง

ไป Capacitor (โหมด remote URL) เป็น Phase 1 เพราะเป็นทางเดียวที่ขึ้น store ทั้งสองพร้อม Full VO ได้โดยไม่ต้อง rewrite โค้ด ~76k บรรทัด (engine 27k + HUD 49k) และงาน Phase 0 (ทำ mobile web ให้ใช้ได้จริง) ต้องทำก่อนอยู่แล้วไม่ว่าจะเลือกตัวไหน

เก็บ Expo ไว้เป็น Plan B ถ้าวัดแล้ว WebView performance ไม่ผ่านเกณฑ์ หรือ Apple ปฏิเสธข้อ 4.2 หลังใส่ native feature ครบ งาน Phase 0 และ push backend ยังใช้ต่อได้ทั้งหมด

ทุกข้อด้านล่างมาจากการอ่านโค้ดใน zyra-app และ repo ข้างเคียง ไม่ใช่การประเมินลอย ๆ

HUD ของ VOviews/user/virtual-office/ ~49k บรรทัด React + TailwindRN/Flutter rewrite UI ทั้งหมด Capacitor ใช้ซ้ำได้แต่ต้องทำ responsive

2. เปรียบเทียบตัวเลือกหลัก

ตารางคะแนน 8 เกณฑ์ ข้อดี/ข้อเสียของ Capacitor, Expo/React Native, Flutter และตัวเลือกอื่นที่ปัดตก แยกไว้ที่หน้า 2 · เปรียบเทียบตัวเลือก

3. แผนงานเป็น Phase

Phase 0 เป็นงานก้อนใหญ่สุดและไม่ขึ้นกับ framework ทำก่อนเสมอ Phase 1 กับ 2 ทำคู่ขนานได้

0zyra-app เท่านั้น

Mobile web ใช้ได้จริง

ต้องทำก่อนทุกอย่าง ไม่ว่าจะเลือก framework ไหน
  1. เอา overlay ออกแบบมี flag เปิดเฉพาะหน้า VO ผ่าน NEXT_PUBLIC_MOBILE_VO=1 ไม่กระทบ prod ระหว่างทำ
  2. Touch control ใน engine virtual joystick + tap-to-walk map เข้า input เดิมของ PixiGameScene ค่า tuning ไป zyra-engine/constants.ts
  3. Viewport + safe area เพิ่ม viewport-fit=cover เฉพาะหน้า VO ใช้ safe-area-inset ใน HUD
  4. Responsive HUD ของ VO chat, member list, meeting bar, zone modal เป็น bottom sheet ต้องมี Figma mobile design ก่อน (rule 10 ห้ามเดา)
  5. Meeting บนมือถือ ซ่อน screen share เมื่อไม่มี getDisplayMedia, ปิด blur / noise-suppressor บนเครื่องอ่อน, เลือกกล้องหน้า/หลัง
  6. Performance profile PixiJS บน iPhone 12 และ Android กลาง ลด resolution, cull, ปิด filters, ลด nature/pet layer บันทึกตัวเลข FPS/memory จริง
  7. Playwright mobile viewport test login → enter workspace → เดิน → เข้า zone
1repo ใหม่ zyra-mobile

Capacitor shell ขึ้น store

repo แยกเพราะ CI ต้องใช้ macOS runner และ signing secret คนละชุด
  1. capacitor.config.ts ตั้ง server.url ต่อ env (dev/uat/prod) และ allowNavigation เฉพาะ domain ของเรา
  2. Native sign-in Google plugin ได้ id_token แล้วเรียก /api/authen/login_google เดิม ฝั่งเว็บเช็ค Capacitor.isNativePlatform() เพื่อสลับปุ่ม และต้องเพิ่ม Sign in with Apple (Apple บังคับเมื่อมี Google login) → endpoint ใหม่ /api/authen/login_apple
  3. Push @capacitor/push-notifications ส่ง FCM token ไป POST /api/user/devices
  4. Lifecycle appStateChange → reconnect WorkspaceWSClient และ SFUClient, iOS เปิด UIBackgroundModes: audio, keep-awake ตอนอยู่ใน VO
  5. Native polish สำหรับ 4.2 splash, status bar, haptics ตอน wave/knock, deep link zyra://workspace/<id> + universal links, หน้า offline native
  6. Permission camera / microphone / notifications ทั้งสอง platform
  7. CI GitHub Actions macOS build iOS + fastlane ขึ้น TestFlight, Android AAB ขึ้น Play internal track, version ผูกกับ tag v* เดียวกับเว็บ
2zyra-api · zyra-notifications · zyra-ws

Push backend

ทำคู่ขนานกับ Phase 1 ได้
  1. zyra-api migration tb_user_device (user_id, platform, fcm_token, app_version, last_seen_at) + route POST/DELETE /api/user/devices ภายใต้ UserGuard + table-driven test
  2. zyra-notifications เพิ่ม provider FCM HTTP v1 (ครอบ APNs และ Android) ข้าง SMTP endpoint ภายใน POST /push secret ผ่าน env JSON
  3. zyra-ws trigger: DM/mention ตอน user offline, knock, meeting invite → ส่งต่อ zyra-notifications
  4. Notification settings ที่มีอยู่ต้องคุมการส่ง push ด้วย
3หลัง store approve

วัดผลและตัดสินใจต่อ

  1. วัด crash-free / FPS จาก Sentry + Mixpanel ที่มีอยู่แล้วบนเครื่องจริง
  2. ตัดสินใจอยู่ Capacitor ต่อ หรือย้ายเฉพาะ screen ที่ performance ไม่พอไป native ตาม Plan B
  3. Screen share บน mobile ผ่าน native plugin ถ้ามี demand

4. ความเสี่ยงที่ต้องเคลียร์ก่อนเริ่ม Phase 1

Apple 4.2 minimum functionality ถ้ากังวลมาก ทางลดความเสี่ยงคือ bundle web asset ใน app ซึ่งต้องแก้ Next.js ให้ export ได้ (ย้าย /api/img ไป zyra-api, เปลี่ยน rewrite proxy เป็นเรียก API ตรง, auth เป็น bearer) งานเพิ่มราว 1 sprint ทำหลัง Phase 1 ได้
Figma mobile design ยังไม่มี Phase 0 ข้อ 4 บล็อกทันทีถ้าไม่มี design เพราะ rule 10 ห้ามเดา spacing/layout
Sign in with Apple เป็นข้อบังคับ ต้องมี Apple Developer account และ Google Play account ก่อนเริ่ม Phase 1
Screen share บนมือถือ อยู่นอก scope รอบแรก ต้องแจ้งลูกค้าล่วงหน้า

5. Verification

Phase 0 (วัดบน iPhone 12 และ Android กลาง เช่น Pixel 6a ผ่าน Safari/Chrome)

  • login → enter workspace → เดินด้วย joystick → นั่งเก้าอี้ → เข้า zone → เปิด mic/cam → ออก ทำได้ครบไม่มี overlay
  • FPS ≥ 30 คงที่ในแมพ 20 คน, memory < 400 MB บันทึกตัวเลขจริงลง progress.md (before คือ "ใช้ไม่ได้ / ถูกบล็อก")
  • Playwright mobile viewport test ผ่านใน CI

Phase 1

  • TestFlight + Play internal build ติดตั้งได้, Google/Apple sign-in native ผ่าน, push ถึงเครื่องเมื่อมี DM ตอน app อยู่ background
  • iOS: ออกจาก app กลางประชุม 30 วินาที กลับมาเสียงยังต่อ, WS reconnect ภายใน 5 วินาที
  • GET /api/health version ตรงกับ app build

Plan B trigger (ย้ายไป Expo)

  • FPS < 20 บน device เป้าหมายหลังปรับ Phase 0 ข้อ 6 แล้ว
  • Apple reject 4.2 สองรอบหลังใส่ native feature ครบ
