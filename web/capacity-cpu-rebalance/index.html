จัดสัดส่วน CPU ใหม่ทั้ง node — ไม่ได้เพิ่ม core

node ยังเป็น e2-standard-4 (4 core) เท่าเดิม — สิ่งที่ทำคือย้าย “ส่วนจอง” (request) จาก environment ที่แทบไม่มีคนใช้ ไปให้ service ที่รับโหลดจริงแทน

คืนคืนมา (dev + uat)
  • api / app / ws: 50m → 10m ต่อ service ต่อ env
  • notifications: 25m → 10m
  • รวม 2 env, 8 service: −270m
ไปเพิ่มที่ (prod)
  • api, ws: 100m → 300m ต่อตัว (กัน CPU-starve ซ้ำ)
  • app: 100m → 500m (คนละ commit เช้าวันเดียวกัน)
  • SFU: request 1500m→1000m · limit 3000m→2500m (media ต้องพังก่อน web/api)

สถานะตอนนี้

ยืนยันแล้ว vs ยังไม่ปิด

ยืนยันแล้ว
  • headroom 370m ที่คืนมายังอยู่ครบ ไม่ขยับกลับเลยใน 12 วัน
  • config ในไฟล์ values.yaml ไม่ถูก revert (เช็คตรงวันนี้)
  • zyra-app ไม่ crash-loop กลับมาอีกเลยแม้แต่ครั้งเดียว
  • CPU ของทุก pod รวม SFU ไม่โดน throttle เลย (0%)
  • zyra-api (Go) นิ่งตลอด ไม่เคยได้รับผลกระทบ
ยังไม่ปิด (คนละสาเหตุ)
  • node 4-core ยังเป็นคอขวดเดิม — item นี้แค่จัดสัดส่วน ไม่ได้เพิ่ม core
  • SFU กิน CPU โต 2 เท่าใน 3 วัน จาก video fan-out (คนละ root cause)
  • zyra-app p95 636ms ยังไม่กลับเป้า <150ms เพราะสาเหตุนี้
  • ทางแก้ (camera 720p) live บน dev/uat แล้ว รอขึ้น prod
อย่าอ่านว่า “ปัญหา capacity จบแล้ว”

การลด CPU ของ dev/uat แก้ปัญหา “แบ่งสัดส่วนไม่เป็นธรรม” ระหว่าง service บน node เดียวกันได้จริง และอยู่ตัว แต่ไม่ได้แก้ “node มีไม่พอ” — ถ้า SFU ยังโตต่อ ต้องตัดสินใจขยาย/แยก node แยกอีกรอบ ไม่เกี่ยวกับ item นี้
